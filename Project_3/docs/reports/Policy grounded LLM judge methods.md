# Make the judge prove what survived

The best available design for our constraints grounds every verdict in quoted evidence, not in better judgement. Haiku names the exact policy clause behind each commitment, quotes where the reply keeps each condition and hedge of that clause, and leaves the verdict to plain code. A verification call runs only on candidate fails, and it re-checks from that evidence instead of challenging the first answer. No published system does this exact task (multilingual customer-service replies with minimal meaning-changing edits), so "state of the art" here means the recipe that 2024–2026 work points to. That work includes RULERS (locked checklist plus quotes checked against the source), CompliBench (most misses come from matching the reply to the wrong rule), reference-side omission checks (AbsenceBench, FineSurE, arXiv 2603.28005) and the cascade evidence against "are you sure?" re-asks. Our `final_judge.py` already has the right skeleton: a self-validating number rule, a structured claim-by-claim call 1, a verify-on-fail call 2 and a tie-break call 3. It has four gaps. A condition can be marked "kept" without evidence. Policy quotes are never checked. Hedge strength is rated after Haiku writes its own English gloss, and Haiku is documented to inflate certainty when it rewrites. And in the default configuration, the structured fields it extracts do not affect the verdict at all. The changes below close those gaps inside the 3-call budget, each behind a default-off switch. **None of them has been measured: no dev numbers exist yet for our judge, and only the baseline's 0.697 combined is measured.** One risk comes before any of this. Under Anthropic API version 2026-10-21, sending `temperature` at any value returns HTTP 400. Our judge sends `temperature: 0` on every call and does not retry a 400, so if the gateway uses that version, every reply fails and the run aborts. The gateway probe must run first, and it must be changed so it can tell this failure apart from a bad key or URL.

## Probe the gateway before anything else: temperature 0 may now be an error

Anthropic's current documentation states: "Starting with API version `2026-10-21`, a request that includes `temperature`, `top_p`, or `top_k` at any value returns a 400 error on every model." On older API versions, the restriction applies to Haiku 4.5 only while thinking is on ([Anthropic thinking docs](https://platform.claude.com/docs/en/build-with-claude/thinking)). Our `_chat` puts `"temperature": 0` into every non-thinking request (`starter_pack/final_judge.py`, line 81). The retry set is `{429, 500, 502, 503, 504}` (`baseline_judge.py`, line 54). Any other status raises `LLMError`, and the failure policy in `docs/ARCHITECTURE.md` says that ends the run. **So under a 2026-10-21 gateway the judge produces no verdicts at all.** The second outcome is quieter. Anthropic's OpenAI-compatible layer says "most unsupported fields are silently ignored rather than producing errors" ([OpenAI SDK compatibility](https://platform.claude.com/docs/en/api/openai-sdk)). A proxy that drops the field without an error would leave both scored runs sampling at the default temperature of 1. Nothing would break, but run-to-run consistency, which is scored, would quietly fall. Even when temperature 0 reaches the model, it is not fully deterministic. There is no `seed`, and the compat layer leaves `system_fingerprint` empty ([OpenAI SDK compatibility](https://platform.claude.com/docs/en/api/openai-sdk)). On other models, temperature 0 still moved accuracy by up to about 15% across 10 runs ([Atil et al.](https://arxiv.org/html/2408.04667v5)).

The current probe cannot diagnose this. `dev_tools/probe_gateway.py` sends `temperature: 0` already in its first "basic call" and exits if that call fails. A temperature rejection therefore shows up as "basic call failed", which looks exactly like a wrong URL or model name. The probe needs three things before it is trusted:

- A **control call without `temperature`**, made first. If the control returns 200 and the temperature-0 call returns 400, the cause is the sampling parameter.
- A **repeat test with a longer, judge-like output**. Three identical 60-token answers are weak evidence that temperature 0 is honoured.
- A check of the **reported model id**. Haiku 4.5 is past its "not sooner than October 15, 2026" retirement date, so a gateway could swap in another model without saying so ([Haiku 4.5 overview](https://platform.claude.com/docs/en/models/haiku-4-5/overview)).

In `final_judge.py`, the matching protection is an `OMIT_TEMPERATURE` switch, read from the environment and off by default, which leaves `temperature` out of the payload. Set it once from the probe result, so that both scored runs send byte-identical requests. A per-call "retry without temperature after a 400" is acceptable as a fallback, but it makes the payload depend on the gateway's answer. Status 529 (overloaded) should also be added to the judge's local retry set ([Anthropic errors](https://platform.claude.com/docs/en/api/errors)). If temperature turns out to be rejected or ignored, consistency must come from short structured outputs and code-side verdicts. That makes the evidence-anchoring changes below more valuable, not less.

## Six ways to build the judge, and which fit our constraints

The literature offers six families of design. The task's rules (claude-haiku-4.5 only, at most 3 calls, stateless, criterion-agnostic) rule two of them out at once.

| Family | What it catches | What it misses | Fits our rules? |
|---|---|---|---|
| Holistic single-pass rubric judge (our baseline) | Surface contradictions and wrong policy details | Omissions and hedges. Judges are "invariant but insensitive" | Yes, but weakest |
| Claim-level support checking, reply → reference (MiniCheck, Vertex Check Grounding, Azure groundedness) | Wrong numbers, unsupported additions, negation flips | Anything absent from the reply | Yes, as one structured call |
| Reference-side inventory, reference → reply (QuestEval recall, FineSurE keyfacts, AbsenceBench placeholders) | Dropped conditions and dropped hedges | Additions, unless combined with the row above | Yes, inside call 1 |
| Compiled locked checklist, quotes checked against the source, calibrated threshold (RULERS) | Generalises to new rubrics | Calibration needs labels (they used 200) | Yes, prompt-only with one global knob |
| Neuro-symbolic policy logic (AWS Automated Reasoning) | Logical contradictions with cited rule IDs | Ambiguous natural language | Clause IDs only; a solver is overkill |
| Fine-tuned checker (CompliBench Qwen3-8B, DynaGuard, Lynx, Bespoke-MiniCheck) | Best published accuracy | n/a | No: the model is fixed |

The case against the first row comes from meta-evaluation. Across 7 judges in the organisers' paper, invariance to harmless edits was about 0.945, but sensitivity to meaning edits was only about 0.319. **Hedge removal (0.210) and condition removal (0.379) were among the least-detected edits.** Claude Haiku 4.5 was the most sensitive judge tested (R 0.561, S 0.917) ([arXiv 2608.24419](https://arxiv.org/html/2608.24419)). Our baseline has the same profile on dev, measured with `score.py`: **catch 0.067 on condition_removal and 0.500 on hedge_removal, against 0.800 on wrong_number and 1.000 on wrong_policy_detail** (`starter_pack/baseline_report.txt`). In FBI, giving a single-answer judge a reference raised its detection of a removed fact from 6% to 48% ([FBI](https://arxiv.org/html/2406.13439)). That is why every serious option above grounds the judge in the policy text.

The second and third rows answer one question: which side gets decomposed? A 2026 prompt-controlled study compared candidate-side atomic decomposition with a holistic judge. **For incomplete answers, holistic judging beat candidate decomposition for every model tested**: Sonnet-4.6 0.430 vs 0.620, GPT-4.1 0.160 vs 0.465. The weaker the model, the larger the loss. The authors' explanation is that with candidate-side decomposition, "nothing in its structure lists what the candidate leaves out" ([arXiv 2603.28005](https://arxiv.org/html/2603.28005)). The study has a caveat: a 60-row check labelled by the author alone reversed the ranking, so the direction is suggestive rather than settled. QuestEval reaches the same conclusion from summarisation. Recall questions generated from the source catch omissions, precision questions catch hallucinations, and only the combination beat either alone (33.5 vs 28.4 and 27.5 average Pearson) ([QuestEval](https://arxiv.org/pdf/2103.12693)). A reply with a dropped condition contains *fewer* claims, so a precision-only check rewards it. Only the policy → reply direction sees it.

The fourth row is the best-evidenced way to carry a judge over to a new criterion without training. RULERS compiles the rubric into a locked, hashed checklist, scores each item with evidence quotes checked against the text, and calibrates once. It beat the baselines in 13 of 16 dataset × backbone cells. **Its ablations show that calibration mattered most (WebNLG 0.614 → 0.504 without it). Locked compilation was worth 0.03–0.07 and evidence anchoring 0.02–0.05** ([RULERS, arXiv 2601.08654](https://arxiv.org/html/2601.08654)). It is a September 2026 preprint without peer review. A related warning: auto-generated rubrics transfer well for linguistic quality but poorly for factual checks (one reported correlation below 0.3) ([GER-Eval](https://arxiv.org/html/2602.08672v1)). Refining a rubric until it passes a benchmark can also cause preference drift ([arXiv 2602.13576](https://www.alphaxiv.org/abs/2602.13576.md)). The criterion text should therefore stay verbatim, with no generated rubric layered on top.

How to spend the extra calls is a separate choice. Majority-of-3 over the same prompt adds +1 to +2.5 balanced-accuracy points only when sampling at temperature above 0. Without sampling it is about the same as a single run ([Rating Roulette](https://arxiv.org/html/2510.27106)). Re-asking the model whether it is sure is worse. **Across 10 LLMs, models flipped 46% of answers when challenged and lost 17% accuracy on average** ([FlipFlop](https://arxiv.org/abs/2311.08596)). Spending calls only when the judge is uncertain, as in Trust-or-Escalate's selective cascades, is the best-founded way to use a fixed budget ([arXiv 2407.18370](https://arxiv.org/abs/2407.18370)). That supports our cascade over voting, provided call 2 checks the evidence independently and is not framed as a challenge.

## The current state of the art is evidence anchoring, not more reasoning

The strongest policy-compliance results come from fine-tuned or frontier models we cannot use. Their failure analyses still show what a prompt-only Haiku judge has to defend against. CompliBench (April 2026) is the closest published analogue to our task: hard, minimal guideline violations in customer-service dialogues for airline, healthcare and insurance. Gemini-3-pro detected violations above 90% of the time in every domain. **For GPT-5, scope mis-attribution caused over 70% of missed violations: the judge mapped the non-compliant action onto a different, compliant rule** ([CompliBench, arXiv 2604.12312](https://www.alphaxiv.org/abs/2604.12312)). That is what a dropped condition looks like from the judge's side. "Free cancellation" with its deadline removed still matches *some* cancellation rule. The fix is to make the judge name the governing clause, quote it verbatim and list that clause's conditions before deciding. Then code can check that the quote exists. On grounding leaderboards, fine-tuned 7B–27B checkers lead LLM-AggreFact at about 77–79.5 balanced accuracy. **No Claude 4.x or Haiku entry exists**, so no external accuracy figure can be quoted for Haiku 4.5 as a checker ([LLM-AggreFact](https://llm-aggrefact.github.io/)). On custom-policy compliance, prompted general LLM judges are competitive: GPT-4o-mini scored 70.1 F1 on DynaBench, while LlamaGuard-3 scored 20.9 ([arXiv 2512.03994](https://arxiv.org/html/2512.03994v3)). That makes a well-structured prompted judge a reasonable bet, not a compromise.

Hedges need their own design, because the model under test distorts them. **When Claude Haiku 4.5 paraphrases medical text, it raises expressed certainty in 20% of examples after one rewrite and 40% after five.** Most models are 1.5–2× more likely to raise certainty than to lower it ([arXiv 2606.07951](https://arxiv.org/abs/2606.07951)). Judges also penalise correct answers that contain weakeners: GPT-4o's accuracy fell from 92.7 to 73.7 ([EMBER](https://arxiv.org/html/2410.20774v2)). Small models comparing certainty or generality between two texts reached only about 0.22–0.33 macro F1 ([Wührl et al.](https://arxiv.org/html/2402.12431v1)). Together, these point to one design: separate ordinal ratings for the policy and the reply, taken from verbatim words, and compared in code rather than judged in one holistic step. Language adds a smaller, steady cost. Moving the same LLMBar items from English to Chinese or a mixed EN/ZH version flipped 14.2% and 12.3% of Haiku 4.5's verdicts, with matching correctness flips. No DE, FR, ES or IT figures exist ([arXiv 2606.14278](https://arxiv.org/pdf/2606.14278)). In multilingual claim matching, the strongest model did better on original-language input than on English translations ([arXiv 2503.02737](https://arxiv.org/pdf/2503.02737)). So the reply should stay in its own language, and the English gloss should be a reasoning aid that is never itself scored.

Putting this together gives the following prompt-only best practice for one Haiku 4.5 with three calls. This is a synthesis, not a measured system:

- **A deterministic layer first.** It covers numbers with units and number words in all five languages. It validates itself on the labelled examples and switches itself off when they contradict it.
- **Call 1 checks evidence in both directions.** The policy is segmented into numbered clauses before any reply is judged. For each commitment in the reply, the model gives the clause ID with a verbatim quote, and each condition and hedge of that clause with the reply span that keeps it, or nothing. It then fills fixed meaning slots (who, where or what, how much, how sure, under what condition, when, what the customer must do). Code checks every quote and computes the candidate verdict.
- **Call 2 verifies only candidate fails.** It sees the locations, not call 1's conclusion.
- **Call 3 is a tie-break.** It runs only when calls 1 and 2 disagree.
- **One global threshold** is chosen on dev and kept for every criterion.

The meaning slots matter for unseen edit types. The organisers' taxonomy includes population widening, domain extension, intensifier addition and tense or modality shift ([arXiv 2608.24419](https://arxiv.org/html/2608.24419)). CompliBench adds missing required actions and invented step dependencies. None of these are in dev, but each falls into one of the slots.

## Our design has the right skeleton, but the evidence is never checked

`final_judge.py` already follows most of this. `prepare()` is deterministic and LLM-free. The number rule self-validates: offline, with no LLM, it fires on **35 of 35 dev wrong_number replies and on none of the 226 originals or 116 harmless edits** (`starter_pack/offline_rule_check.py`). On the synthetic stress set, though, it fires on 30 of 35 harmless stricter-number edits (`docs/ARCHITECTURE.md`). Call 1 lists policy conditions per claim, which is the reference-side direction. Examples are chosen deterministically, in alternating label order. Call 2 runs only on candidate fails and is told that dropping a condition while still stating the entitlement is a change of meaning. The gaps are in the details, and each one maps to a finding above.

| Practice from the evidence | `final_judge.py` today | Gap |
|---|---|---|
| Absence made explicit, with proof (AbsenceBench, QuestEval) | `"status": "kept"` needs no quote | Haiku can say "kept" without pointing at any text. This is the main remaining risk for condition_removal |
| Governing clause quoted and checked (CompliBench, RULERS) | `policy_rule` is free text and never checked | Scope mis-attribution is unguarded. A paraphrased or wrong clause passes silently |
| Reference-side conditions listed before reading the reply's wording (2603.28005) | Claims are pulled from the reply first, and conditions are attached to them | If `policy_rule` is null, no conditions are listed and the omission cannot be seen. An unsupported promise with a null rule is never acted on |
| Verdict computed in code from the extracted fields | The default verdict uses only the model's `violates_criterion` booleans. `_differences()` exists but runs only under `SECOND_LOOK=False` | A dropped condition or higher certainty that the model recorded itself can still pass |
| Certainty rated from the original words (2606.07951, EMBER) | `gloss_en` comes before the certainty fields. The 0–3 scale mixes may/usually/always with some/all | Inflation from the gloss can cause false fails on translations, and quantifier edits can be counted twice or not at all |
| Independent verification, not a challenge (FlipFlop) | "Another reviewer says the reply violates…", with the reviewer's reasons included | Anchoring, and because call 2 only sees fails, drift toward "pass" costs catch |
| Fixed meaning slots for unseen edit types | Only `scope: wider/narrower` | Population, domain, time and required-action edits have no field |
| Short, bounded outputs (Atil et al.) | `MAX_TOKENS=3000`, no length guidance | Longer outputs correlate with lower run-to-run agreement |
| Number rule covers values with units and number words | Digits only, and bare values | "zwei Wochen" and "trente jours" are invisible. A wrong value that happens to appear elsewhere in the policy passes |
| Gateway robustness | `temperature: 0` always sent; 400 and 529 not retried | See the first section |

Two parts of the current design are worth defending. First, `_differences()` is deliberately symmetric: stricter and looser differences both go to the verifier, and the criterion text decides. Hard-coding "only looser is bad" would build criterion-specific logic into code, which the rules forbid. The cost is the EMBER-style bias toward failing hedged or stricter replies, so watch false fails on those paths. Second, the cascade is the better use of the budget than voting at temperature 0, as long as call 2 is de-anchored.

## Ten changes, ranked, each behind a default-off switch

The ranking weighs expected change in the harmonic-mean score against evidence strength and risk. It concentrates on condition_removal: as one of four harmful types in a macro average, raising its catch moves combined the most. **These are expected effects, not results.** Each change is built behind a switch that defaults to off, tested with mocks, and then run with `bash run_dev.sh` (3-fold cross-validation grouped by `source_id`) twice for consistency, plus leave-one-edit-type-out, the stress set and the two mock criteria. The ship rule is the one already in `docs/ARCHITECTURE.md`: combined must rise by at least 0.02 on dev **and** on stress, with no harmless type losing more than one case of keep and no loss of consistency. Dev has only 9 source replies, and one item moves a type's rate by about 3–7 points, so ties keep the default. Every setting must be decided before the 14:30 criterion arrives. From then until the 16:00 freeze, the frozen code runs unchanged.

| Rank | Switch (default off) | Change | Targets | Evidence | Main risk |
|---|---|---|---|---|---|
| 0 | `OMIT_TEMPERATURE` env; add 529 to the retry set; fix the probe | Probe first; leave out temperature if the gateway rejects it | Every run | Anthropic 2026-10-21 docs | None to verdicts; robustness only |
| 1 | `SECOND_LOOK` (exists) | Send differences that call 1 recorded itself to call 2 | condition_removal, hedge_removal | Reference-side recall (2603.28005, QuestEval) | More call-2 traffic and more false fails; already built, so the cheapest to measure first |
| 2 | `CONDITION_EVIDENCE` | Add `evidence_quote` to each policy condition. In code, "kept" with an empty quote or one not found in the reply (fuzzy `difflib` match) becomes "dropped" | condition_removal | AbsenceBench placeholders; QuestEval recall | Translated or paraphrased conditions fail the substring match, which costs translation keep |
| 3 | `CLAUSE_IDS` | `prepare()` splits the policy into numbered clauses without an LLM. Call 1 cites the ID plus a verbatim quote, and code checks it. A mismatch routes to call 2 as "ambiguous" | wrong_policy_detail, unseen scope edits | CompliBench scope mis-attribution; RULERS evidence anchoring; AWS rule IDs | Longer prompt; segmentation must stay generic |
| 4 | `CONDITIONS_FIRST` | Reorder call 1 so it copies the matched clause's conditions verbatim before it reads the reply's wording. Treat a promise with a null rule as an unsupported candidate | condition_removal, added commitments | arXiv 2603.28005 | More candidates, so more call-2 load |
| 5 | `HEDGE_FROM_QUOTE` | Rate certainty from the original-language quote, add verbatim `hedge_words_reply`, and remove some/all from the certainty anchors so quantifiers go to scope | hedge_removal, translation keep, quantifier widening | arXiv 2606.07951; EMBER; Wührl et al. | A prompt change can shift other types; check with leave-one-edit-type-out |
| 6 | `VERIFY_DEANCHOR` | Call 2 gets the quoted locations and clause IDs, without "another reviewer says" or the reasons, and re-derives each one | Catch preserved through call 2 | FlipFlop; Huang et al. on self-correction | Could confirm more harmless differences |
| 7 | `MEANING_SLOTS` | Replace `scope` with population, domain, time and required-action fields | Unseen edit types in the hidden set | 2608.24419 taxonomy; CompliBench | Longer output, which costs consistency (Atil et al.) |
| 8 | `NUMBER_WORDS`, `NUMBER_UNITS` | A small number-word lexicon for EN/DE/FR/ES/IT with guards for articles; compare (value, unit) pairs | wrong_number, written-out numbers | Value-plus-unit checking (arXiv 2512.16189) | "un/ein/uno" read as 1 can switch the rule off; check self-validation |
| 9 | `BRIEF_OUTPUT` | Cap the number of claims and allow one sentence per field | Consistency, kappa | Length vs agreement (arXiv 2408.04667) | Truncated claim lists |
| 10 | `LEXICON_HINTS` | Neutral, two-sided lists of modal, condition and negation differences, shown in call 2 only and validated in `prepare()` | Dropped conditions, hedges | Anchoring results (arXiv 2412.06593, 2605.23970) argue for caution | Anchoring; ship only if leave-one-edit-type-out holds |

Changes 2, 4 and 5 are prompt and schema edits to call 1. Build them separately, so the experiment log can attribute any gain to one of them. `ADJUDICATE`, which already exists, is worth one run as a control for call 3, because the default tie-break discards both reviewers' evidence. Several popular options should stay off for the scored runs:

- **Extended thinking.** On Haiku 4.5 it forces the default temperature and disables prefill, so it trades scored consistency for an accuracy gain nobody has shown ([Anthropic thinking docs](https://platform.claude.com/docs/en/build-with-claude/thinking)).
- **Same-prompt majority-of-3 at temperature 0.** It is mostly wasted budget (see the Rating Roulette results above).
- **Any LLM call inside `prepare()`.** It could build a different checklist on each scored run.
- **Any response cache.** It breaks the no-state rule and would fake the consistency score.

## Conclusion

The research changes what "improving the judge" means for this task. The literature does not offer a cleverer question to ask Haiku. It offers a way to make Haiku's answer checkable: quoted clauses, quoted conditions and ordinal fields that code compares and the model cannot argue away. That also targets the two scored properties together. Recall on omissions comes from the reference-side inventory, and run-to-run stability comes from verdicts that depend on short fields rather than free text. The same structure is what generalises to the 14:30 criterion, because it checks dimensions of meaning, not known edit types.

The order of work is therefore fixed by risk, not ambition. First, run the corrected probe and settle `OMIT_TEMPERATURE`, because a 400 on every call would make the rest of this list irrelevant. Next, measure the switch that already exists (`SECOND_LOOK`), then add evidence quotes and clause IDs. Write nothing into `RECIPE.md` or `SUBMISSION.md` until `score.py` produces it. Every number in this report about our own judge is either the baseline's or explicitly marked as expected.
